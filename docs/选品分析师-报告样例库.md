## 样例 A：✅ 建议入场

### 场景
宠物免洗清洁喷雾 200ml 猫狗通用（液体精华形态）。1688 采购价 $1.5；DIRECT 标准化售价 $25-30；DIRECT 数 15 个；3/3 关键词成功；销售信号 15/15。差异化 + 合规 IP 核验均完整。

### 关键参数
- **快速成本**：采购 $1.5 + 佣金 15% + FBA $3.43 + 退货 5% + 广告 10% + 优惠券 $1.0
- **全成本（低/基准/高）**：包装 $0.2/$0.3/$0.5 + 国内物流 $0.2/$0.3/$0.5 + 头程 $0.5/$0.8/$1.2 + 关税 $0.2/$0.3/$0.5 + 清关 $0.1/$0.2/$0.3 + 入仓 $0.2/$0.3/$0.5 + 仓储 $0.1/$0.15/$0.2
- **目标贡献利润率**：10%
- **复算结果**：基准全成本贡献利润率 39.3% > 10%；悲观全成本贡献利润 $8.57 > 0

### 覆盖章节
- ✅ 第一部分：本品基础信息解析（9 行齐全，含 1688 采购价 + 包装尺寸 + 款式属性 + 应用场景 + 缺口提示）
- ✅ 第二部分：目标平台细分市场调研（18 样本 / 15 DIRECT / 2 ADJACENT / 1 NON_COMPARABLE + 3 关键词 100% 成功）
- ✅ 第三部分 3.1：DIRECT 竞品汇总表（4 个真实 ASIN 品牌 + 售价 + 评分 + 评论 + BSR + 徽标）
- ✅ 第三部分 3.2：竞品评论意见聚合（按 ASIN 聚合好评 / 差评 / 来源 URL）
- ✅ 第三部分 3.3：竞品详情页 bullet 摘要（brand + SKU + seller + 截前 2 bullet + 80 字符限）
- ✅ 第四部分：价格、成本与单位经济（DIRECT 标准化售价 P25/中位/P75 + 快速成本 + 全成本）
- ✅ 第五部分：合规、知识产权与差异化核验（≥ 8 字符）
- ✅ 第六部分：入场结论（✅ 建议入场，决策可追溯）

### evidence 等级
- 事实：1688 商品页 / Amazon 详情页 / Amazon 评论页
- 外部估算：FBA 履约费 / Amazon 佣金率
- 分析假设：采购价（全成本其他费用、目标贡献利润率、差异化、合规/IP）

### 决策可追溯
- 系统入场结论：✅ 建议入场
- 报告最终结论：✅ 建议入场
- ✅ 完全一致

## 样例库使用建议

### 给 AI 智能体
1. **生成新报告前**：先读 `docs/选品分析师-报告模板-v1.2.md`（模板）→ 再读本样例库（标准答案）→ 然后再调纯函数
2. **多示例优于少示例**：在 prompt 中提供 ≥ 2 个样例（A 成功 + C 拒绝）能显著降低误解模板概率
3. **决策可追溯**：智能体必须把"系统入场结论"和"报告最终结论"放在同一行，便于用户校验

### 给用户/审阅人
1. **比对样例 vs 实际报告**：检查第一/第三部分是否被真实数据填实（不是"待验证"占位）
2. **决策可追溯校验**：系统入场结论 = 报告最终结论，二者必须完全一致
3. **决策理由解读**：
   - ✅ 建议入场：可直接进入采购 / 试单阶段
   - ⚠️ 有条件谨慎入场：补齐缺项证据后可重新判定
   - ❌ 不建议入场：调整成本/售价/目标后重新复算
   - ❓ 数据不足：补齐 evidence 后重新复算

### 给开发者
- 4 个样例都是 `.tmp-ui-verify/sample-generator.mjs` 生成，参数化驱动
- 新增样例：在 `scenarioConfigs` 数组追加一个对象，标注期望决策
- 决策断言：`if (decision.decision !== expectedMap[s.label]) process.exit(1)` 强制对齐

## evidence 字段完整列表（23 个）

`evaluateAmazonEntryDecision` 内部使用的 `DECISION_EVIDENCE_FIELDS` 包含 23 个字段，分为 3 组：

### 快速成本组（6 字段）
- `purchaseCostUsd` — 采购价（USD）
- `referralFeeRate` — Amazon佣金率
- `fbaFulfillmentFeeUsd` — FBA履约费（USD）
- `returnLossRate` — 退货损耗率
- `advertisingRate` — 广告费率
- `couponCostUsd` — 优惠券成本（USD）

### 全成本组（21 字段，三档 low/base/high）
- `packagingQcUsd` — 包装/质检（低/基准/高）
- `domesticFreightUsd` — 国内物流（低/基准/高）
- `firstLegFreightUsd` — 头程（低/基准/高）
- `dutyUsd` — 关税（低/基准/高）
- `customsClearanceUsd` — 清关（低/基准/高）
- `inboundUsd` — 入仓（低/基准/高）
- `storageUsd` — 仓储（低/基准/高）

### 决策参数组（3 字段）
- `targetContributionMargin` — 目标贡献利润率（必须在 {10, 15, 20, 25} 中选一个）
- `differentiationEvidence` — 差异化核验依据

## 边缘场景补充说明

1. **DIRECT 样本不足 15 个**：直接走 `❓ 数据不足`，与是否有利润无关（见样例 D 之外的"低样本"场景）
2. **价格无法标准化**：DIRECT 标题不含 200ml 等可解析单位时，`normalizedDirectPrices` 返回空数组，走 `❓ 数据不足`
3. **targetContributionMargin 选 30%**：不在白名单 {10, 15, 20, 25} 中，直接走 `❓ 数据不足`，系统不替用户假设门槛
4. **完全无销售信号**：audit.salesSignalCount=0 时，即使其他都满足也走 `❓ 数据不足`
5. **同 ASIN 多来源**：API + 页面双源抓取时，API 字段优先，页面仅补全 API 缺失字段

## Word (.docx) 导出链路（F 阶段新增）

### 目的
把 6 部分 markdown 报告导出成可发给工厂/客户/团队直接打开使用的 `.docx` 文档，章节结构、表格、超链接全部保留。

### 实现
- **纯函数**：`src/shared/reportWordExport.ts`（319 行）
  - `reportMarkdownToDocxBuffer(markdown, options)` → `Promise<Buffer>` 生成 .docx 二进制
  - `reportMarkdownToDocxFile(markdown, filePath, options)` → 写入磁盘
  - `extractReportMetadata(markdown)` → 返回 H1/H2/H3/表格/段落/链接数等元数据（供 verify 工具使用）
- **依赖**：`docx@^9.7.1`（npm `docx` 库，内部用 jszip 打包 OOXML）
- **设计原则**：
  1. 纯函数幂等：相同输入两次输出 size 差 ≤ 64 字节（ZIP 时间戳字段可漂移）
  2. 不依赖 Electron：可在 Node 端跑通
  3. 不修改 6 部分结构：纯转换，决策可追溯链路不动

### Markdown → docx 映射表

| Markdown | docx 元素 | 字号 / 样式 |
|---|---|---|
| `# 标题` | Heading 1 | 22pt 黑体加粗 |
| `## 二级标题` | Heading 2 | 16pt 加粗 |
| `### 三级标题` | Heading 3 | 13pt 加粗 |
| `- 列表项` | bullet list | 11pt 宋体 |
| `1. 列表项` | numbered list | 11pt 宋体 |
| `> 引用` | blockquote（缩进 + 灰字） | 11pt 斜体灰 |
| `\| col \| col \|` | Table（带表头 + 边框） | 表头加粗 + 灰底 |
| `---` | 水平分割线 | 浅灰 |
| `**bold**` | 加粗 run | 11pt 加粗 |
| `` `code` `` | 等宽 run | Consolas |
| `[text](url)` | 超链接 | 蓝色下划线 |
| 普通段落 | Normal | 11pt 宋体 |

## I.5 阶段：守卫软同步（保留 docId + RAGFlow update_doc）

### 入库目标

- UI 可一键切换 `soft ⇄ hard`，切换后立即调 `kbGuardian:update-skill` 写回持久化
- 运行时支持 `runNow(id, { syncMode })` 临时覆盖（不改持久化，仅本次 runNow 生效）

|------|---------------|---------------|-------------------|----------|

## I.6 阶段：守卫孤儿文档清理

### 入库目标

把 I.2 / I.5 阶段的「同步当前源目录」补全为「同步 = 同步当前 + 清理孤儿」：

- **背景问题**：守卫跟踪 `hashes[skillId][relPath] → docId`，但 `runSkill` 只处理「当前 files[] 中的文件」。一旦用户从源目录删 1 个文件、重命名 1 个文件，KB 中残留的旧 `docId` 永远不会被清理，**长期运行会累积大量孤儿文档污染 KB**。
- **补齐后行为**：每次运行完文件循环后，新增孤儿扫描：`Object.keys(hashes[skillId])` diff vs `files[]` → 不在 files 里的 relPath 视为孤儿 → 调 `deleteDocs` 清除 + 从 `hashes` 清掉 entry。
- **受 `options?.orphanCleanup !== false` 控制**（缺省 `true`，向「后兼容」倾斜；运行时 `runNow(id, { orphanCleanup: false })` 可临时关闭）
- **统计透明**：`orphansRemoved` 计入 `GuardianRunLog` + `GuardianSkillStats.orphansRemoved`，UI 仅当 `> 0` 时显示「🧹 孤儿清理 N」灰底 chip。
- **预置技能默认 `orphanCleanup: true`**（launcher 显式声明 + 漂移检查）。

## I.7 阶段：软→硬回退（I.5 resilience 补全）

### 入库目标

把 I.5 阶段的「软同步失败只能 push failure 卡住文件」补全为「软同步失败自动回退到硬同步」：

- **背景问题**：I.5 软同步上线后，`update_doc` 失败时（docId 失效 / RAGFlow 0.11- 老版本 / RAGFlow 临时故障）守卫进入「软同步更新失败」partial 状态，**该文件永远卡住**——orphan 不会清、hashes 不会更新、每次 run 都会再次失败。用户必须手动从 KB Web UI 删旧 docId 或把 syncMode 切到 hard 才能恢复。
- **补齐后行为**：软同步 try/catch 内 catch 时**自动硬回退**：调 `deleteDocs` 删旧 docId + `uploadAndParse` 传新文件 + 重解析。docId 失效的文件也能继续同步，不会卡死守卫。
- **受 `options?.softFallbackHard !== false` 控制**（缺省 `true`，向「恢复力」倾斜；运行时 `runNow(id, { softFallbackHard: false })` 可临时关闭，保留 I.5 行为）
- **统计透明**：`fallbackToHard` 计入 `GuardianRunLog` + `GuardianSkillStats.fallbackToHard`，UI 仅当 `> 0` 时显示「🔁 软→硬回退 N」灰底 chip（描边琥珀色 `#fcd34d` 与孤儿 chip 区分）。
- **预置技能默认 `softFallbackHard: true`**（launcher 显式声明 + 漂移检查）。
- **与 orphan 清理的协同**：回退成功后 `hashes[relPath] = { hash, docId: 新 docId }`，旧 docId 已被 deleteDocs 清掉，I.6 孤儿扫描无影响。

### 软→硬回退架构图

```
┌──────────────────────────────────────────────────────────────┐
│  文件循环：当前 files[] 中的每个文件                          │
│  ├─ 新增 → uploadAndParse（hard 路径）                       │
│  ├─ hash 相同 → skipped                                     │
│  └─ hash 变化（effectiveSyncMode = soft）：                  │
│       ├─ 软同步 try：updateAndParse(entry.docId, absPath)   │
│       │     ├─ ✅ 成功 → updated++ · continue               │
│       │     └─ ❌ 失败（docId 失效/老 RAGFlow）              │
│       │            │                                          │
│       │            ▼  I.7 新增：自动硬回退                   │
│       │       ┌──────────────────────────────────────┐       │
│       │       │  受 options?.softFallbackHard 控制    │       │
│       │       │  ├─ true（默认）：                    │       │
│       │       │  │   deleteDocs([oldDocId])           │       │
│       │       │  │   uploadAndParse(absPath)          │       │
│       │       │  │   → updated++ · fallbackToHard++ │       │
│       │       │  │   → continue                       │       │
│       │       │  └─ false（I.5 行为）：              │       │
│       │       │      push failure · continue         │       │
│       │       └──────────────────────────────────────┘       │
│       │            软+硬双错时：                            │
│       │            failures.push("软同步+硬回退均失败：软=...；硬=...") │
└─────────────────┬────────────────────────────────────────────┘
                  │  fallbackToHard=1
                  ▼
┌──────────────────────────────────────────────────────────────┐
│  RAGFlow KB                                                  │
│    回退后：旧 docId 已被删除，新 docId 已上传重解析          │
│    hashes[relPath] = { hash, docId: 新 docId }              │
└──────────────────────────────────────────────────────────────┘
```

### 回退语义

| `softFallbackHard` | 行为 | 适用场景 |
|------|------|---------|
| `undefined`（缺省）| ✅ 自动硬回退 | 默认路径（I.7+）：docId 失效/RAGFlow 老版本时自动恢复 |
| `true` | ✅ 自动硬回退 | launcher 显式声明 / 运行时显式开启 |
| `false` | ❌ 只 push failure（I.5 行为） | 调试场景 / 用户想保留旧 docId 不被删 / 误删恢复中 |

**软+硬双错处理**：`updateAndParse` 抛错 → 进入硬回退 try/catch → 硬回退也失败 → push `软同步 + 硬回退均失败：软={msg}；硬={msg}` 到 `failures`，**不**抛错外层（保持守卫继续运行）
